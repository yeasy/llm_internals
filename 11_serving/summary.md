## 本章小结

在[技术全景图](../01_introduction/1.0_technology_map.md)中，本章连接模型执行与在线服务。全章只有一条线：Decode 每步至少把权重读一遍，这笔固定成本只能靠批来摊；批的上限是 KV 显存；调度、分页、前缀复用都是在同样的显存里放进更多序列、少算重复的部分；多卡把带宽和显存加起来，分离把 Prefill 的干扰隔出去；衡量这一切的是满足延迟目标的到达率，不是吞吐。下面八条规律沿这条线排列，每条注明成立的条件与量级。

**一、读权重是固定成本，批是唯一的摊法。** 上下文不长时，Decode 一步的耗时由“权重 + 各请求的 KV”除以显存带宽决定，与批里有几个请求几乎无关。Llama 3 8B 在 H100 上，批从 1 加到 32，每步只从 4.83 ms 慢到 6.05 ms，吞吐上界却涨到 25.6 倍；批摊薄的只有权重，KV 各读各的（11.1 节）。

**二、批的上限是 KV 显存，调度只认词元。** 连续批处理让结束的请求立即让位（11.2 节）；分页让 KV 按需分配，同一个约 41 万词元的池，平均 1,000 词元的请求从预分配时的 50 个增加到 408 个（11.2.3、11.4 节）。调度器不分 Prefill 与 Decode，一步只决定给每个请求几个词元：预算低于约 340 个词元时白付读权重的时间，高于词元间隔目标允许的长度时拖慢同批的 Decode；显存用尽时抢占，今天的引擎只做重算（11.3 节、11.4.5）。

**三、少算重复的部分，但省不到读权重以下。** 前缀复用让命中 2,000 个词元的请求 Prefill 计算量降到 9.8%，耗时却受读一遍权重的下界所限，线上命中率也只有五到七成（11.5 节）。多 LoRA 不合并权重，一个 `r = 16` 的适配器只占基座的 0.5%，分段内核让不同适配器的请求同批计算（11.6 节）。约束解码的掩码必须藏进前向：朴素实现每张 3.21 ms，有索引与缓存后降到几十微秒，再与前向重叠（11.7 节）。

**四、多卡把带宽与显存加起来，通信必须留在低延迟域内。** 张量并行同时换来时延和吞吐，但每层两次 all-reduce 卡在关键路径上；Decode 的消息只有 MiB 量级，耗时是“通信步数 × 固定开销”，Llama 3 70B 在 8 卡环形算法下一步有 2,240 个串行通信步。流水线并行只换来容量，时延不降；专家并行把词元送到专家所在的卡，专家组越大，专家的批越接近算力受限（11.8 节）。

**五、分离买的是词元间隔的尾部，不是吞吐。** 32 条 4K 序列的纯 Decode 一步 13.7 ms，掺进一个 2,048 词元的 Prefill 块就成了 184 ms；分块只能把干扰切碎。分离的代价是 KV 过网络、Prefill 池的显存不驻留在途序列、两池配比随流量漂移；网络速率高于 Prefill 的 KV 产生速率并留数倍余量、规模大到两池取整后仍满载时才划算（11.9 节）。

**六、CPU 段必须藏进 GPU 段。** Llama 3 8B 一步 Decode 有三百多个内核，平均每个只运行十几微秒，与 CPU 侧每个内核一份的提交成本同量级。CUDA Graph 把逐个提交换成一次回放，内核融合省掉中间读写，重叠调度让 CPU 比 GPU 早一步（11.1.2、11.14 节）。vLLM 与 SGLang 独立收敛到同一组做法：缓存算作空闲，控制面只存块号或下标，新词元留在 GPU 上，分词移出调度进程；两者的差别在前缀索引是哈希表还是一棵向调度器暴露结构的树（11.10、11.11 节）。

**七、带宽定单流，容量定并发，批大小定成本。** 单流 Decode 的上界是显存带宽除以权重字节，Llama 3 70B 的 FP8 权重在 H200 上约 69 词元/秒。批处理有一条推不过的线：4K 上下文下算术强度的极限约 112，低于 H200 的 FP8 拐点 412，长上下文的 Decode 开多大的批都受带宽限制。同一张 H200 上批 32 与批 1 的每百万词元成本相差 20 倍，所以先把批开大，再考虑换卡（11.12 节）。

**八、衡量看 Goodput 与词元间隔的高分位。** 排队使延迟目标在利用率远没到 1 时就失守：固定服务时间的例子里，TTFT 不超过 1 秒、达标率 90% 的 Goodput 只有饱和吞吐的 54%，服务时间重尾时更低。TPOT 是请求内平均，会抹平卡顿，流畅度要看词元间隔的高分位。GPU 利用率在带宽受限时同样很高，不能作扩容信号（11.13 节）。

**今天默认怎么做。**

- 引擎：连续批处理、分页 KV、前缀缓存、分块 Prefill、重叠调度与 CUDA Graph 全部打开（11.1.3、11.10 节）。
- 并行度：单节点内取装得下且时延达标的最小张量并行度，不出 NVLink 域、不超过 K/V 头数，其余的卡做副本；流水线并行只在跨节点或没有 NVLink 时使用（11.8.8）。
- 部署形态：默认合置加分块 Prefill；规模大、输入长、词元间隔要求严时才分离，并按有效输入长度逐请求决定走哪条路（11.9.5）。
- 选卡：Decode 按带宽与容量选，Prefill 按算力选；比较每百万词元成本，不比卡价（11.12.7）。
- 压测与容量：开环压测、用真实的长度分布与前缀结构、在客户端计时；按 Goodput 定实例数，并留出峰值与故障余量（11.13.2、11.13.3）。
- 扩容与过载：看排队时间、KV 占用与抢占次数，不看 GPU 利用率；等待队列设上限，尽早拒绝（11.13.4）。
- 排障：先在时间线上找 GPU 在等谁，内核之间有空隙是在等 CPU，停在集合通信处是在等别的卡（11.14.4）。

1. Llama 3 8B 在 H100 上，批从 32 加到 128，每步的下界从 6.05 ms 升到 9.80 ms。两种批下的总吞吐上界各是多少？为什么每步变慢而总吞吐上升？（[11.1.1](11.1_engines_overview.md)）
2. KV 池 53.94 GB、每词元 131,072 字节，能放多少个词元？请求平均长 1,000 个词元时，按最大长度 8,192 预分配与按块大小 16 按需分配，各能同时放下多少个请求？（[11.2.3](11.2_continuous_batching.md)、[11.4.1、11.4.2](11.4_kv_memory_management.md)）
3. Llama 3 70B 在 `t = 8` 下，64 个请求各走一步 Decode，通信的带宽项只有 0.65 ms，为什么通信仍可能比 5.3 ms 的读权重下界更慢？环形算法共有多少个串行通信步，换成每次 2 步的算法后是多少？（[11.8.4](11.8_multi_gpu_inference.md)）
4. 32 条 4K 序列的 Decode 一步 13.7 ms，同一步里加进一个 2,048 词元的 Prefill 块后是多少？TBT 上限定为 50 ms 时，块最长多少个词元？分块为什么消除不了这种干扰？（[11.9.1](11.9_disaggregated_serving.md)）
5. SGLang 的准入余额为什么要减去按 `ρ` 打折的预留量？空闲 20,000 个槽位、可淘汰 30,000 个，40 个运行中的请求各剩 800 个词元未生成，`ρ = 0.7` 时余额是多少？下注输了会发生什么？（[11.11.4](11.11_sglang_internals.md)）
6. Llama 3 8B 的 SwiGLU 激活经内核融合与录进 CUDA Graph，各省掉哪一种开销？Decode 批 32 时融合省下的主要是字节还是一次提交？vLLM 为什么对超过 512 个词元的批不用图？（[11.14.2](11.14_gpu_software.md)、[11.10.5](11.10_vllm_internals.md)）
7. H200 的显存带宽是 4.8 TB/s，Llama 3 70B 的 FP8 权重是 70 GB，单流 Decode 的上界是多少词元/秒？批 32、每条序列 1.34 GB 的 KV 时，每流速度与总吞吐各是多少？（[11.12.2](11.12_hardware.md)）
8. 一台实例的饱和吞吐是 2.72 请求/秒，在 TTFT 不超过 1 秒、达标率 90% 的要求下 Goodput 为什么只有 1.47？只看吞吐做容量规划，会把工作点定在哪里？（[11.13.2](11.13_best_practices.md)）
