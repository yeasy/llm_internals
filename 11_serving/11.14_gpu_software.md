## 11.14 GPU 软件栈：从张量到内核与通信

张量公式规定计算什么，GPU 软件栈决定如何执行。前面各节已多次用到这一层的概念：[10.1 节](../10_inference_optimization/10.1_bottleneck.md)与 [11.1 节](11.1_engines_overview.md)指出小批 Decode 的时间耗在内核启动上，[11.10.5](11.10_vllm_internals.md) 用 CUDA Graph 压缩这笔开销，11.10.4 与 [11.11.5](11.11_sglang_internals.md) 各用到一个 Triton 内核，[11.8 节](11.8_multi_gpu_inference.md)的 all-reduce 由通信库执行。本节把这些概念放回同一个软件栈，说明内核、融合、CUDA Graph 与 NCCL 各自减少哪一种开销，排障时怎样区分。

排查推理性能，需要把框架算子、设备程序、任务提交和跨卡通信分开：同一个矩阵乘法变慢，可能来自内核选择，也可能来自提交间隙或等待其他 GPU。全节用一行代码 `y = relu(x + b)` 贯穿，其中 `relu(z) = max(z, 0)`：11.14.1 看它怎样变成内核，11.14.2 算它的访存与提交开销，11.14.4 用它说明排障时应当看到什么。

<a id="gpu-kernels"></a>

### 11.14.1 从 PyTorch 算子到 GPU

算子是加法、矩阵乘法等张量操作；内核（kernel）是在 GPU 上执行的设备函数，两者并非一一对应。`y = relu(x + b)` 在 PyTorch 默认的逐句执行（eager）模式下是加法与 ReLU 两个算子，各启动一个内核，中间结果 `t = x + b` 先写进显存，再被第二个内核读出。每个算子从 Python 调用到 GPU 开始计算，要过三步：

- **派发。** PyTorch 的派发器依据张量设备和自动求导等状态选择实现；该实现可以调用已有计算库，也可以启动一个或多个内核。具体派发机制见 [PyTorch 官方教程](https://docs.pytorch.org/tutorials/advanced/dispatcher)。
- **提交。** 在 NVIDIA 路径中，CUDA 是编程与执行平台，提供内存管理、流和内核启动等接口（见 [CUDA 平台说明](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html)）。流（stream）表达有序提交的工作，内核连同参数被排进流里。
- **执行。** GPU 按流的顺序执行设备代码。

前两步在 CPU 上完成，每个内核各走一遍，耗时与张量大小无关；第三步的耗时随数据量增长。11.14.2 的两种优化分别作用于不同的步骤。

> [!NOTE]
> **进阶：Runtime 与 Driver API。** 上述接口由 CUDA Runtime 提供，它依赖驱动；Driver API 提供更显式的上下文、模块与执行控制。框架也可直接使用 Driver API，并非每次调用都必须逐层穿过 Runtime。参见 [Runtime 与 Driver API 的区别](https://docs.nvidia.com/cuda/cuda-runtime-api/driver-vs-runtime-api.html)。

**编译路径。** `torch.compile` 增加了编译路径：TorchDynamo 捕获计算图，默认后端 TorchInductor 优化并生成代码，GPU 路径使用 Triton 作为重要组件。对 `relu(x + b)`，编译器通常把两个逐元素算子合成一个内核，这就是 11.14.2 的融合。这里的 Triton 是编写、编译 GPU 内核的语言与编译器；[NVIDIA Triton Inference Server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/index.html)则是提供模型推理服务的软件，两者职责不同。编译也不意味着所有操作都会变成一个内核，见 [PyTorch 编译器文档](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/torch.compiler.html)。Triton 内核也可以直接手写：11.10.4 中 vLLM 计算写入槽位的内核、11.11.5 中 SGLang 改写 logits 的内核都属于这一类。

**两种图。** 应据此区分两种图：框架计算图描述张量操作及数据依赖，供编译器分析和改写；CUDA Graph 描述设备工作的提交依赖，供运行时反复执行。捕获到框架图只是编译入口，并不能据此判断已经消除了中间张量，也不能证明服务请求的排队时间变短。以 `relu(x + b)` 为例：录进 CUDA Graph 后它仍是两个内核，`t` 照样写回显存，省下的是逐个提交的 CPU 开销；经编译器融合后才只剩一个内核，`t` 不再落到显存。

### 11.14.2 分块与融合：一次向量计算的账

设输入 `x`、`b` 是各含 1,000,000 个 FP32 元素的连续向量，输出为同长度的 `y = relu(x + b)`，其中 `relu(z) = max(z, 0)`。例如前三项为 `x = [-2, 1, 3]`、`b = [1, 2, -5]`，输出对应为 `[0, 3, 0]`。

**分块。** 一个内核内部把数据分成块并行处理。按 [Triton 向量加法教程](https://triton-lang.org/main/getting-started/tutorials/01-vector-add.html)的分块方式，每个程序实例负责 1,024 个连续元素，共需 `⌈1,000,000 ÷ 1,024⌉ = 977` 个实例；最后一个仅有 `1,000,000 − 976 × 1,024 = 576` 个有效元素，用掩码阻止越界读写。一个实例处理一块数据，不等于启动 1,024 个线程，线程映射由编译器与启动配置共同决定。

**融合省的是中间读写。** 假设未融合时先执行加法内核，把中间向量 `t` 写回全局内存，再执行 ReLU 内核。忽略缓存、对齐和其他开销，逻辑读写量为：读取 `x`、`b`，写入 `t`，读取 `t`，写入 `y`，共 `5 × 1,000,000 × 4 = 20 MB`。融合内核在片上保留加法结果并立即取最大值，只读两个输入、写一个输出，共 `3 × 1,000,000 × 4 = 12 MB`，减少 40%，还少一次内核启动。这里 MB 按百万字节计，逻辑流量不等于实际 HBM 流量。

融合（fusion）因此改变计算的内核边界，消除中间读写；它不保证加速，收益取决于形状、缓存、寄存器压力和原有实现。

**CUDA Graph 省的是提交开销。** [CUDA Graph](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)记录操作及依赖、实例化后重复提交，主要摊薄启动准备开销；它可以仍包含多个内核，不会仅因捕获就消除 `t`。两种优化可以组合，不能互相替代。

**能省多少。** 提交开销是每个内核一份的固定成本，GPU 执行时间则随批增大，两者之比决定收益。小批 Decode 一步要启动数百到上千个内核（10.1 节），每个内核只处理几十行数据，固定成本的占比最高。量级可以参照两组公开数字：

- 驱动一层：NVIDIA 的[入门示例](https://developer.nvidia.com/blog/cuda-graphs/)在 V100 上测一个执行时间为 2.9 微秒的内核：每个内核提交后都等它完成，平均每个 9.6 微秒；连续提交、不逐个等待，是 3.8 微秒；20 个内核录成一张图后是 3.4 微秒。
- 框架一层：每个内核提交之前还有 Python 与 C++ 各层的参数准备和派发，回放一张图把这些层次连同驱动开销一并跳过。[PyTorch 官方博客](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/)报告的例子是 MLPerf 训练基准中 Mask R-CNN 的骨干网络：每卡批大小为 1 时，录图的部分从 31 ms 降到 6 ms。同文指出，批大时 CPU 开销占比可以忽略，批小时它可以超过 GPU 的运行时间。

批大到执行时间占主导后，收益随之消失。vLLM 对超过 512 个词元的批不用图，原因在此；它的尺寸表、整图与分段图的取舍见 11.10.5，下面只讲捕获的一般条件。

**捕获的条件。** 以 PyTorch 常见的捕获/重放（capture/replay）路径为例，应先在旁路流预热，再捕获形状、布局和控制流稳定的区域，并长期持有输入、输出缓冲区，保证重放使用同一内存地址。新请求可以把新 token 值复制到原输入缓冲区；改变值并不等于可以改变捕获时的批大小、布局或 Python 分支，见 [PyTorch CUDA Graph 使用说明](https://docs.pytorch.org/docs/main/notes/cuda.html#cuda-graphs)。

**动态批怎么办。** 动态请求可按形状分桶，为各桶捕获图，并用填充适配实际批次。例如只捕获批大小 1、4、8，3 个请求填充到 4 后使用对应图，并正确屏蔽填充项；也可只捕获稳定子区域，对未覆盖形状或不支持的操作回退普通 eager 执行。参见 [PyTorch 动态形状说明](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/torch.compiler_cudagraph_trees.html#dynamic-shape-support)、[局部捕获](https://docs.pytorch.org/docs/main/notes/cuda.html#partial-network-capture)和 [NVIDIA 批大小调优示例](https://nvidia.github.io/TensorRT-LLM/latest/blogs/tech_blog/blog20_Tuning_CUDA_Graph_Batch_Sizes_for_Higher_Output_Throughput.html)。维护多份图及长期缓冲区可能增加显存占用，填充增加无效计算，反复捕获也有成本；收益取决于形状复用率及 CPU 提交是否构成瓶颈。

> [!NOTE]
> **进阶：图更新与条件节点。** 上述条件针对常见框架路径，常规服务按这些静态约束理解即可。CUDA 底层还提供受约束的 [图更新](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html#updating-instantiated-graphs)和 [条件节点](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html#conditional-graph-nodes)，可修改部分节点参数或表达设备端分支、循环；不能据此断言所有 CUDA Graph 都只支持静态工作负载。

### 11.14.3 NCCL：让多张卡交换结果

前两小节都在一张卡之内。模型切到多卡后，各卡每层都要交换中间结果，这类通信由通信库完成。NCCL 是 GPU 通信库，提供 AllReduce、AllGather、ReduceScatter 等集合通信，即参与设备共同完成约定的数据交换或归约。例如两张卡分别持有 `[1, 2]` 和 `[3, 4]`，求和 AllReduce 后两卡都得到 `[4, 6]`；张量并行为何需要这类操作，见 [11.8 节](11.8_multi_gpu_inference.md)。

NCCL 根据拓扑组织传输与计算；NVLink、PCIe、InfiniBand 等互连承载数据。通信库与硬件不是替代关系，安装 NCCL 不会让 PCIe 连接获得 NVLink 带宽。NCCL 支持节点内和跨节点通信，并与 CUDA 流集成，见 [NCCL 概览](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html)。

通用通信库与推理引擎自带的通信内核各有分工。11.8.4 的算例里，Llama 3 70B 在 TP8 下一步 Decode 有 160 次 all-reduce，64 个请求时每次的消息只有 1 MiB，耗时几乎全是每个通信步的固定开销。推理引擎因此为小消息另写步数固定的 all-reduce 内核，较大的消息仍交给通用通信库。

### 11.14.4 按等待位置诊断

诊断看的是时间线。Nsight Systems、[PyTorch Profiler](https://docs.pytorch.org/docs/stable/profiler.html) 一类剖析工具把每个内核画成时间轴上的一段：段的长度是执行时间，段与段之间的空白是 GPU 在等待。先固定输入形状、精度和批量，核对输出，再区分首次编译与稳定执行。随后按时间线上的形态判断等待发生在哪一层：

- **GPU 内核之间有空隙。** GPU 在等 CPU。追查 CPU 提交、同步和依赖。上文 PyTorch 博客的 Mask R-CNN 即是这种画面：CPU 负载 100%，GPU 大部分时间空闲，内核之间留有大片空白；录图之后内核紧密相接。
- **单个内核耗时长。** 时间花在内核内部。比较计算量、访存量和实际吞吐；`relu(x + b)` 融合前后的 20 MB 与 12 MB 就是这样一笔访存账。
- **大量短内核连续出现。** 每段很短而段数很多，固定成本占比高。评估融合与 Graph。
- **跨卡等待占主导。** 各卡停在集合通信处互相等待。再核对通信量、拓扑及各卡到达集合操作的时间。

先定位等待发生在哪一层，再改对应配置，避免把计算、启动和通信问题都归因于“GPU 不够快”。

前述算例给出了可检查的预期：融合后应少一个内核和中间张量读写；启用 Graph 后应检查提交开销是否下降，以及图覆盖的批次、重捕获与回退频率、填充比例和显存增量；调整多卡通信后应检查暴露在关键路径上的等待是否减少。最后回到相同负载下的端到端延迟与吞吐。局部流量减少是机制证据，整条请求变快才是服务收益，两项需要分别记录。
