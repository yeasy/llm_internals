## 11.14 GPU 软件栈：从张量到内核与通信

一个算子从 Python 走到 GPU，CPU 侧的派发与提交是每个内核一份的固定成本，执行时间才随数据量增长。Llama 3 8B 在 H100 上一步 Decode 读权重的下界是 4.79 ms（[11.1 节](11.1_engines_overview.md)的常量表），而这一步要发射三百多个内核，平均每个只运行十几微秒，固定成本与执行时间同一量级。软件栈上的优化都在这笔账的某一项上做文章：**内核融合**改变内核边界，省掉中间张量的读写，对访存受限的逐元素算子有效；**CUDA Graph** 不改内核，把逐个提交换成一次回放，省掉 CPU 逐个派发、提交内核的时间，这段时间在 GPU 上表现为内核之间的空隙，计入 [11.1.2](11.1_engines_overview.md) 式子里的 $t_{\text{GPU}}$；两者作用在不同的项上，可以叠加。通信库负责多卡之间的集合通信，带宽由互连决定。排障看时间线：内核之间有空隙是 GPU 在等 CPU，各卡停在集合通信处是在等别的卡。

本节汇总 [10.1 节](../10_inference_optimization/10.1_bottleneck.md)、[11.10.5](11.10_vllm_internals.md) 与 [11.8 节](11.8_multi_gpu_inference.md)已经用到的这些概念。

<a id="gpu-kernels"></a>

### 11.14.1 从 PyTorch 算子到 GPU

算子是加法、矩阵乘法等张量操作；**内核**（kernel）是在 GPU 上执行的设备函数，两者并非一一对应。每个算子从 Python 调用到 GPU 开始计算要过三步：PyTorch 的派发器按张量的设备与状态选出实现（**派发**）；实现通过 [CUDA](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html) 把内核连同参数排进一个流，流里的工作按提交顺序执行（**提交**）；GPU 运行设备代码（**执行**）。前两步在 CPU 上，每个内核各走一遍，耗时与张量大小无关；第三步的耗时随数据量增长。

**一步 Decode 有多少个内核。** 在融合较充分的实现里，Llama 3 8B 的一层约有十个内核：两次归一化（各与残差相加合成一个）、四次矩阵乘法（QKV、输出投影、gate 与 up 合并、down）、旋转位置编码、写 KV、注意力、激活。32 层就是三百多个，读权重的 4.79 ms 摊下来每个约 15 微秒；逐算子执行、不做融合时内核数上千，平均每个只剩几微秒。批越小，每个内核越短，固定成本的占比越高。

**编译路径。** `torch.compile` 用 TorchDynamo 捕获计算图，默认后端 TorchInductor 优化并生成代码，GPU 上的内核多由 **Triton** 生成。Triton 是编写、编译 GPU 内核的语言与编译器，也可以直接手写内核：[11.10.4](11.10_vllm_internals.md) 中计算写入槽位的内核即是。它与 [NVIDIA Triton Inference Server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/index.html) 同名而职责不同，后者是提供模型推理服务的软件。编译不保证所有操作合成一个内核（[PyTorch 编译器文档](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/torch.compiler.html)）。

框架的计算图与 CUDA Graph 是两种图：前者描述张量操作及数据依赖，供编译器分析和改写，融合发生在这里；后者描述设备工作的提交顺序，供运行时反复回放，不改变内核本身。

### 11.14.2 分块与融合：一次向量计算的账

一个内核内部把数据分成块，交给 GPU 上的许多计算单元并行处理，越界的部分用掩码屏蔽。内核之间的数据则要经显存交接，融合要省的就是这一段。

**融合省的是中间读写。** 以 Llama 3 8B 的 SwiGLU 激活 `y = silu(g) ⊙ u` 为例，`g`、`u` 是 gate 与 up 两路输出，每个词元各 14,336 维，BF16。不融合时，第一个内核读 `g`、写中间结果 `s = silu(g)`，第二个内核读 `s` 与 `u`、写 `y`，共五次整张量的读写；融合后在片上算完，只读 `g`、`u`、写 `y`，三次，访存减少 40%，还少一次内核提交。

收益多大取决于批。Decode 批 32 时每张量只有 `32 × 14,336 × 2 ≈ 0.92 MB`，五次读写按 3.35 TB/s 只要 1.4 微秒，融合省下的 0.5 微秒不及一次提交的固定成本，这时真正省下的是那一个内核。8,192 词元的 Prefill 每张量 235 MB，融合每层省约 140 微秒，32 层合 4.5 ms，约为这次 Prefill 计算时间的 1.3%（计入注意力后，[11.3 节](11.3_scheduler_loop.md)表 11-5 末行的峰值下界 134 ms 按 40% 利用率折算约 330 ms）。规律是：融合对逐元素运算、归一化、残差相加这类访存受限的小算子有效，因为省掉的读写就是它们的全部成本；对已经受算力或权重读取限制的大矩阵乘法几乎无效。收益最大的融合在注意力里：FlashAttention 不把 `n × n` 的分数矩阵写回显存（[10.3 节](../10_inference_optimization/10.3_flash_attention.md)）。今天的引擎把这几类分开处理：注意力用 FlashAttention 一类的专用内核，矩阵乘法交给厂商的矩阵库，残差相加与归一化、SiLU 与逐元素乘、旋转位置编码各写成手工融合的内核，其余由 `torch.compile` 生成。

**CUDA Graph 省的是提交开销。** [CUDA Graph](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html) 记录一串内核及其依赖，实例化后整体提交。它仍包含原来的每个内核，中间张量照样写回显存；省掉的是逐个派发与提交的 CPU 时间。量级可以参照两组公开数字：

- 驱动一层：NVIDIA 的[入门示例](https://developer.nvidia.com/blog/cuda-graphs/)在 V100 上测一个执行时间为 2.9 微秒的内核：每个内核提交后都等它完成，平均每个 9.6 微秒；连续提交、不逐个等待，是 3.8 微秒；20 个内核录成一张图后是 3.4 微秒。
- 框架一层：每个内核提交之前还有 Python 与 C++ 各层的参数准备和派发，回放一张图把这些层次连同驱动开销一并跳过。[PyTorch 官方博客](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/)报告的例子是 MLPerf 训练基准中 Mask R-CNN 的骨干网络：每卡批大小为 1 时，录图的部分从 31 ms 降到 6 ms。同文指出，批大时 CPU 开销占比可以忽略，批小时它可以超过 GPU 的运行时间。

批大到执行时间占主导后，收益随之消失，vLLM 对超过 512 个词元的批不用图就是这个原因。回放要求形状、布局与显存地址固定：输入写进长期持有的静态缓冲区，动态的批按大小分桶、各录一张图并填充到最近的已录尺寸（[PyTorch 的 CUDA Graph 说明](https://docs.pytorch.org/docs/main/notes/cuda.html#cuda-graphs)、[TensorRT-LLM 的批大小调优示例](https://nvidia.github.io/TensorRT-LLM/latest/blogs/tech_blog/blog20_Tuning_CUDA_Graph_Batch_Sizes_for_Higher_Output_Throughput.html)）。代价是多份图的显存、填充行的无效计算和启动时的捕获时间，vLLM 的取舍见 11.10.5。

<a id="nccl"></a>

### 11.14.3 NCCL：让多张卡交换结果

模型切到多卡后，各卡每层都要交换中间结果。NCCL 是 NVIDIA 的 GPU 通信库，提供 AllReduce、AllGather、ReduceScatter 等集合通信：两张卡分别持有 `[1, 2]` 和 `[3, 4]`，求和 AllReduce 后两卡都得到 `[4, 6]`。通信库按拓扑选算法、组织传输，并与 CUDA 流集成（[NCCL 概览](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html)）；带宽由 NVLink、PCIe、InfiniBand 这些互连决定，换库换不来互连没有的带宽。

推理里还有一层分工。[11.8.4](11.8_multi_gpu_inference.md) 的算例中，Llama 3 70B 在 TP8 下一步 Decode 有 160 次 all-reduce，每次的消息只有 1 MiB，耗时几乎全是每个通信步的固定开销。推理引擎因此为小消息自带步数固定的 all-reduce 内核，较大的消息仍交给通用通信库。

### 11.14.4 按等待位置诊断

诊断看的是时间线。Nsight Systems、[PyTorch Profiler](https://docs.pytorch.org/docs/stable/profiler.html) 一类工具把每个内核画成时间轴上的一段：段的长度是执行时间，段与段之间的空白是 GPU 在等待。先固定输入形状、精度和批大小，区分首次编译与稳定执行，再按时间线上的形态判断等待发生在哪一层：

- **内核之间有空隙。** GPU 在等 CPU，追查 CPU 提交、同步和依赖。上文 PyTorch 博客的 Mask R-CNN 即是这种画面：CPU 负载 100%，GPU 大部分时间空闲；录图之后内核紧密相接。
- **单个内核耗时长。** 时间花在内核内部，比较它的计算量、访存量和实际吞吐，判断它离 Roofline 的哪条线更近（10.1 节）。
- **大量短内核连续出现。** 每段很短而段数很多，固定成本占比高，评估融合与 CUDA Graph。
- **跨卡等待占主导。** 各卡停在集合通信处互相等待，核对通信量、拓扑及各卡到达集合操作的时间。

改完一项，先看对应的局部证据（内核数、提交间隙、关键路径上的通信等待）是否下降，再看相同负载下的端到端延迟与吞吐，后者才是服务收益。
